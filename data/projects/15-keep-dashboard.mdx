# keep-dashboard

I moved most of what I run from the cloud to one box at home. An old 8th-gen i5, 6 cores, 32GB of RAM, a 1TB SSD and a 225GB one. I call it the keep. Tailscale gets me in, AdGuard does DNS, Uptime Kuma checks everything and pings my phone through ntfy, and Dokploy deploys the apps.

Once it ran, I wanted one screen that told me the state of it. I tried the existing dashboards and none of them matched my taste: monochrome, boxy, sharp corners. So I wrote my own, on Bun with React and no UI library. It is open source under MIT, and the live one sits behind my tailnet at [keep.findmalek.engineer](https://keep.findmalek.engineer/). That link is gated, so you will see a refusal. The point of this page is what is behind it.

## The pages

Six of them, all black and white. The only colors are orange and red, and they mean one thing: close to a limit, or at it. Nothing else is allowed to be colored, so when something is, I look.

## One snapshot every second

![Flow diagram: collectors refresh every second, five seconds, fifteen seconds, thirty seconds and five minutes, merge into one snapshot on each tick, which goes to the browser over server sent events and to SQLite as one minute averages kept for 31 days.](/project/keep-dashboard/snapshot-flow.png)

_Fast things are read each tick, slow things keep their own timer._

One Bun process collects everything and pushes a snapshot to the browser every second over Server-Sent Events. Not everything can be read that fast. CPU and memory can. Asking Dokploy for its projects cannot. So each collector runs on its own timer and writes only its own fields, and the one second tick just merges whatever they last produced. Long-term history, 1 minute averages and peaks for 31 days, goes into SQLite and feeds the 1h to 30d tabs.

Every integration is optional. If one is not configured its panel hides or says it is not reachable.

## The container cannot run anything on the host

The dashboard has buttons that can reboot the machine. A web app that can do that is a bad idea if it also holds a shell.

![Diagram: the dashboard container writes a request file into a shared folder, a systemd path unit wakes a Python host agent, and the agent accepts only reboot, tidy, a known job or a configured switch and refuses everything else.](/project/keep-dashboard/host-agent.png)

_A button drops a file. Only the host agent decides what happens._

So the container never runs host commands. A button drops a request file into a shared folder. A systemd path unit notices it and starts a small Python agent on the host. The agent accepts `reboot`, `tidy`, `run:<known job>` and start or stop of a switch I configured. Everything else is refused and logged. It even refuses a reboot if the box booted less than five minutes ago. Requests also need a custom header, so another website cannot trigger them from my browser.

Even if someone owned the web app, the worst they could do is drop a file the agent refuses.

![Schedule of host jobs across a day: a status refresh every minute, the cleanup at 04:30 every day, and the tidy at 05:00 on Sundays.](/project/keep-dashboard/jobs-schedule.png)

_The timers behind the jobs page._

The jobs are plain systemd timers. The nightly cleanup runs at 04:30. The weekly tidy runs Sundays at 05:00: stopped containers, old images, build cache, old journal logs, the apt cache. It never touches Docker volumes or my data. A status timer rewrites the job state every minute so the page stays honest.

## What was wrong, and what I did

The first release was too open. Any container on the same Docker network could call the API and press its buttons, and the Docker socket was mounted into the dashboard. A read-only mount on a socket does not make the API read-only, which surprised me. I fixed it within four days.

![Four stacked layers drawn generically: a private route that only answers my own devices, a gate header, a read-only Docker proxy, and the host agent allowlist.](/project/keep-dashboard/layers.png)

_Four layers, drawn without any real hostnames or values._

- **A private route.** The dashboard is reachable through a route that only my devices can use.
- **A gate.** That route adds a header carrying a long secret, and every API call without it is a 403. The check is constant time. The proxy overwrites whatever a client sends, so it cannot be forged from the outside. The health check stays open for uptime.
- **A proxy for Docker.** The socket left the dashboard. A small proxy on its own internal network forwards exactly one request, listing containers. Not inspect, since that would expose other containers' environment.
- **The agent.** Buttons only ask, as above.

I added CI and a test for the gate in the same change, because there had been no tests at all.

Two lessons were not about security. The 7 day and 30 day graphs looked broken, because history only goes back to the day the dashboard went live. Range tabs now clear old data at once and say where history starts. And my cleanup once deleted a sleeping game server and its image, because it looked stopped and unused. Now the tidy job skips containers labeled as sleepers, and the jobs page has start and stop buttons for those.

The general lesson I took from the open issue: Docker edits the firewall itself when it publishes a port, so a rule you wrote can be skipped without you noticing. I found that in an audit and the fix is still open. I am not going to describe the details of my own box here.

## Power cuts

Tunisia has frequent power cuts. I set the BIOS so the box powers on by itself when the electricity comes back, and it boots straight into everything it was running. The dashboard is how I check that it actually came back. The uptime in the header tells me whether it rebooted while I was away.

## What is still rough

- No login of its own. It relies on being reachable only through the tailnet, which is fine for me and a bad default for anyone else.
- The published ports issue above is open.
- The agent is about 330 lines of Python with no tests. The server side has a few small ones, for the gate, the Docker proxy, jobs, outages and range labels.
- No alerts of its own. Uptime Kuma and ntfy do that.
-

## What is next

The jobs page already has a placeholder for an offsite backup, planned for when new drives arrive. The login is the next thing I would add, since it is the biggest gap in the list above.
