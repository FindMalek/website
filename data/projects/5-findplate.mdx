# FindPlate

FindPlate is a generator. `bunx findplate create` copies a turborepo template, renames it to your project, removes the modules you didn't ask for, and then does the setup work that usually takes a day: agent rules, a first commit, a GitHub repo with a project board and a ruleset, CI, and pull request previews.

The code is on [GitHub](https://github.com/FindMalek/findplate) and the docs and landing page are at [plate.findmalek.engineer](https://plate.findmalek.engineer). It's MIT licensed. The reason it exists is written up in [Why I built FindPlate](/blog/why-i-built-findplate).

This is the second version. The first one was a Next.js starter you clone and then delete from. I kept it on the [`v1` branch](https://github.com/FindMalek/findplate/tree/v1) and rewrote the project as a CLI. The v2 work started with [issue #3](https://github.com/FindMalek/findplate/issues/3), "v2: cli and project template".

## The problem

I ship a lot of projects, and I keep building the same ones. This site has 15 case studies. Three of my repos, [dukkani](/projects/dukkani), [sonaraem](/projects/sonaraem) and `lyterion`, each have an `apps/api` and an `apps/dashboard`, and the same `auth`, `common`, `config`, `db`, `env`, `orpc` and `ui` packages. Five of my repos carry a `pr-auto-assign.yml` workflow. Every time, I rebuilt that structure by hand or copied it from the last repo.

v1 didn't fix that. It was one Next.js app with Prisma, Supabase, next-intl and a waitlist form, and you removed what you didn't want after cloning. What I wanted instead: you run one command and everything is set up, even the readme, the GitHub project and the agent rules.

The first step does most of the work. It copies [`template/`](https://github.com/FindMalek/findplate/tree/4624929/template), rewrites the placeholder scope `@acme` to your project's, strips the modules you turned off, swaps the theme tokens for your preset's, and writes a `.env` with generated secrets and an admin password. `postgresPort` is the first free port from 5432, so the generated compose file doesn't collide with a database you already run.

The output is a plain turborepo. Nothing at runtime imports findplate.

## What you get

| Piece | What it is |
| --- | --- |
| `apps/web` | the landing page, with a live status window |
| `apps/dashboard` | better-auth login and an app shell |
| `apps/api` | oRPC on bun, the only app that touches the database |
| `apps/docs` | optional fumadocs site about your project |
| `packages/ui` | shadcn components and the preset's theme tokens |
| `packages/common` | zod schemas, constants and utils shared by every app |
| `packages/orpc`, `db`, `auth`, `env` | typed rpc, drizzle on Postgres, better-auth, zod-validated env |

## Architecture

The one structural rule I took from my own repos: `apps/api` is the only app that touches the database, auth, storage and providers. The web app and the dashboard only talk to it through the typed oRPC client. The one thing a frontend imports from `auth` is `@acme/auth/client`, which talks back to the api.

A missing key turns a feature off instead of crashing the app. Storage, AI, email, WhatsApp and Telegram return `null` from their factory and the code that uses them checks for it, so a fresh project always starts.

Tooling is fixed on purpose: pnpm in the project, bun for the api, Biome for format and lint, strict TypeScript, one root `.env`. The [why page](https://plate.findmalek.engineer/docs/why) has the table of choices and the reasons. There's one orm, one auth library, one rpc layer. There's no second option.

## The module system

There are 17 modules: `storage`, `ai`, `docs`, `rate-limit`, `email`, `whatsapp`, `webhooks`, `telegram`, `umami`, `openobserve`, `glitchtip`, `infisical`, `langfuse`, `waitlist`, `roadmap`, `status` and `databuddy`. `storage`, `ai`, `docs` and `rate-limit` are on by default. `telegram` requires `webhooks`, `langfuse` requires `ai`, and `create` switches required modules on with the one you picked.

A module is three things: a package, its env keys, and the lines of code that use it. The manifest, [`template/findplate.json`](https://github.com/FindMalek/findplate/blob/4624929/template/findplate.json), lists the paths to delete, the packages to drop from every `package.json` and the pnpm catalog, the keys to ask for, and what it requires. The lines of code are marked in the source with comments:

```ts
// @findplate:ai
import { createAi } from "@acme/ai"
// @end
```

A trailing `// @findplate:ai` marks a single line. Markers come in four comment styles (`//`, `#`, `{/* */}` and `<!-- -->`) and can't nest. I picked markers over a templating language because the template is real code. It's type-checked and tested in the repo, so a broken template fails my own CI and not someone's first run.

### Adding and updating later

A generated project is not a dead end. The state file records the name, preset, pitch, enabled modules and the template version the project was made from, and two commands use it.

`findplate add ai` regenerates the template with and without the module and applies only the difference: new files, changes in shared files where you haven't edited them, missing keys appended to `.env`. Files you changed are listed, never overwritten, and it refuses to run on a dirty git tree (exit code 3).

`findplate update` renders the template of the recorded version and the newest one, then does a three-way merge per file with `git merge-file`: your file, the old template, the new template. It leaves your edits alone where the template didn't change, and writes conflict markers where both touched the same lines. `findplate doctor` checks the environment (env keys, database, node, pnpm, gh) and exits `1` on a failing check.

## Agents and workflow

Every generated project has one source of rules, [`.ruler/AGENTS.md`](https://github.com/FindMalek/findplate/blob/4624929/template/.ruler/AGENTS.md): the stack, structure, naming, commit format, test style and the oRPC, drizzle and better-auth conventions. [ruler](https://github.com/intellectronica/ruler) turns that into what each coding agent reads: `CLAUDE.md`, `AGENTS.md`, `.cursor/`, `opencode.json` and `.zed/`, for Claude Code, Cursor, opencode, Zed and oh-my-pi. The generated files are committed, so a fresh clone works without ruler. The same config gives each agent the context7, shadcn and Vercel MCP servers.

Seven project skills ship in `.ruler/skills`, for the workflow around a ticket: `dive-ticket`, `plan-ticket`, `ship`, `review-ticket`, `triage-reviews`, `check-touched` and `clean-pr`. They're built around GitHub issues and the project board, and they only commit or push when you invoke `ship`. These are the same commands I use in my own setup, written up in [my dotfiles post](/blog/dotfiles-that-keep-every-agent-on-the-same-rules). `create` also installs public skill packs, and a pack that can't be fetched is skipped with a note.

With `--github`, or a yes at the prompt, `create` also sets up the GitHub side with the `gh` cli:

- the repo, with your pitch as the description, delete branch on merge, and `main` pushed
- labels (`bug`, `feature`, `task`, `docs`, `blocked`, `p0` to `p2`) and milestones (`Foundation`, `Launch`, `Later`)
- a project board with the columns Backlog, Ready, In progress, In review and Done
- repo variables and secrets from your `.env`, sent through stdin so values never show in the plan or the process list
- a ruleset on `main`: a pull request is required, and `ci` and the PR hygiene check must pass

The plan is plain data in [`plan.ts`](https://github.com/FindMalek/findplate/blob/4624929/packages/cli/src/github/plan.ts). The executor runs it, `--dry-run` prints it, and the tests read it. Every step treats "already exists" as done.

Three of the workflows in the generated repo keep that setup alive: `ci`, `pr-hygiene` (the PR needs an issue link and commits in the `type(scope): subject` format with five words or fewer) and `project-status`, which moves the issue a PR closes to In review and then to Done on merge.

## CI and previews

CI in the findplate repo generates a project and checks it, so a template change can't break `create` without a red build. [`module-matrix.mjs`](https://github.com/FindMalek/findplate/blob/4624929/.github/scripts/module-matrix.mjs) builds the matrix from `template/findplate.json`: one job per module generated alone (with what it requires), one with all modules and one with none. That's 17 + 2 = 19 jobs, and each runs lint, types and tests. On a pull request only the all-modules and minimum jobs also run the build, the rest build on pushes to `main`. A new module needs no CI edit, the matrix picks it up from the manifest. Two more jobs check that the schema has no uncommitted migration drift and run Lighthouse on the generated landing page.

Production deploys from `main` on Vercel (the docs and landing page you can open are that setup). Pull requests don't. The preview workflow is set up so each PR gets its own preview per app on a [Dokploy](https://dokploy.com) server, though it has only run against a mock server so far:

- one Dokploy application per app, at `pr-<number>-<app>.<PREVIEW_DOMAIN>`
- a GitHub deployment per app, so the PR shows **View deployment**
- one sticky comment, updated in place on every push, in the style of the Vercel bot: app, status (Building, Ready, Failed), preview link, inspect link, and an error excerpt when a build fails
- cleanup when the PR closes

The logic lives in plain node scripts in [`.github/scripts`](https://github.com/FindMalek/findplate/tree/4624929/template/.github/scripts) with no dependencies. Without the Dokploy settings the workflow exits green and says what is missing. Drafts and forks are skipped, since forks can't read secrets. `findplate provision` can also create the Dokploy projects, S3 buckets, DNS records, Turborepo cache secrets and a nightly `pg_dump` backup workflow.

## Design presets

A preset is a folder in `presets/`: a `preset.json` and a `theme.css` of shadcn tokens. There are five. `monochrome` (black and white, square corners, IBM Plex and JetBrains Mono) is the default and the one this site's look comes from. The others are `clay`, `editorial`, `midnight` and `soft`. The cli lists whatever it finds in the folder, so adding a preset is adding a folder.

The components are shadcn, living in your repo. To change the look later, edit the css variables in `packages/ui` or paste a theme from [shadcn create](https://ui.shadcn.com/create).

## Engineering challenges

The generator is mostly about not breaking, and the real bugs in the history are about that.

**A stripped module has to leave clean code.** Removing a marked block is the easy part. The generated project then gets linted, and Biome rejects a doubled blank line or a blank line right after a bracket. [`tidyBlankLines`](https://github.com/FindMalek/findplate/blob/4624929/packages/cli/src/generate/strip.ts) exists for that. Marker blocks inside an array literal were worse. In `apps/api/src/server.ts` the `glitchtip` and `openobserve` interceptors were marked entries of one array, so what came out depended on which of them were on. [`bbcf387`](https://github.com/FindMalek/findplate/commit/bbcf387) replaced the literal with an empty array and one `interceptors.push(...)` line per module, each with a trailing marker, so every combination produces ordinary code.

**Import order has to survive the strip.** Marked imports in the template were out of Biome's order (`@acme/whatsapp` sat before `@acme/telegram`), so a generated project failed its own lint. I fixed the order in [`2aa0799`](https://github.com/FindMalek/findplate/commit/2aa0799) and [`9da8ded`](https://github.com/FindMalek/findplate/commit/9da8ded). The one-line marker form exists so a line stays attached to its own import when the formatter reorders imports. Step 5 of `create` runs `pnpm check` for the same reason: the first commit shouldn't contain code the project's own linter would change.

**A duplicate key in the catalog.** `pnpm-workspace.yaml` is a catalog of dependency versions that modules add to and strip from. The template's catalog had `@next/env` listed twice at the same version, and [`6464828`](https://github.com/FindMalek/findplate/commit/6464828) is a one-line fix that removes the second. Duplicates are easy to create when several modules each add their own entries.

**The state file made the tree dirty.** `findplate add` and `update` refuse to run on a dirty git tree, so a user can always `git restore .`. After `create` ran its first commit, though, the tree was dirty: the `git` step was marked done in `.findplate/state.json` after the commit, so the state file changed after it. That was [issue #59](https://github.com/FindMalek/findplate/issues/59). The step is now recorded before `git add -A`, so the first commit contains the state that says it happened.

**A related one: where the commit goes.** If the target sits inside another git repository, `git init` plus a commit would commit a new project into the outer repo, for example when you generate into a monorepo. [`68d284e`](https://github.com/FindMalek/findplate/commit/68d284e) skips the step with a note when the directory is already inside a repository.

**The first real GitHub run.** I ran `findplate github` for real against a private throwaway repo (since deleted). It created the repo, labels, milestones, CODEOWNERS, templates, workflows, 10 repo variables, 2 secrets and a project board with the Status columns. It also found two things mocks couldn't. The plan added an https remote while my `gh` is configured for ssh, so the push failed ([issue #78](https://github.com/FindMalek/findplate/issues/78), [PR #79](https://github.com/FindMalek/findplate/pull/79), [`a646ae3`](https://github.com/FindMalek/findplate/commit/a646ae3)): the remote now follows `gh config get git_protocol`. And the ruleset on `main` failed with HTTP 403, because rulesets need a paid plan on private repos. The step reports that and carries on.

**Spinners in a log.** A spinner is great in a terminal and noise in a CI log or an agent transcript. [Issue #61](https://github.com/FindMalek/findplate/issues/61): [`tasks.ts`](https://github.com/FindMalek/findplate/blob/4624929/packages/cli/src/tasks.ts) prints one plain line per step when stdout isn't a terminal. For the same reason every prompt has a flag, so `-y` plus flags never asks anything.

**The v1 to v2 rewrite.** v1 had 75 commits and ran from April 2024 to December 2025, the last being a merge of a React Server Components CVE fix. The tag `v1-final` marks it, and the branch is still there. v2 is a rewrite, not an upgrade: a starter you delete from was the original problem, so polishing v1 wasn't an option. The v2 pull requests landed on October 27 and 28, 35 of them, after the issues were filed on October 17.

## What isn't proven

Most of the tests don't talk to real services. The Dokploy preview workflow, the `provision` calls (Dokploy, S3, DNS), Resend, Telegram and the Kapso WhatsApp module are tested with mocks and fake fetch calls, and I haven't run them against live accounts. Some response shapes of the Dokploy API are assumed in [the docs](https://plate.findmalek.engineer/docs/provision) and live in one function so they're easy to correct. The ruleset on `main` has never run on a repo where it is allowed. A first real run of the rest will probably find something, because the GitHub step did.

Also, as of today, `findplate` is not on npm yet. The release workflow publishes on a version tag, and I haven't pushed one. Until then the cli runs from a clone of the repo: `pnpm install`, then `pnpm dev create ../demo --name demo -y`.

## Status

Work in progress, and public. It's on `0.1.0` in the changelog with 17 modules, 5 presets and 35 merged v2 pull requests. The landing page and docs are live, and the `/docs` section was rebuilt in the landing's boxed brand. What's next is the first npm release, running the provisioning against real services, and fixing the docs pages that still describe the plan rather than the code.
