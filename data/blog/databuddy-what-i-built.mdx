Databuddy is an analytics platform that doesn't track people in creepy ways. It started open source. In 2026 it went closed source, and `github.com/databuddy-analytics/Databuddy` now returns a 404.

My work did not go with it. I kept a full local clone and a public fork, [FindMalek/Databuddy](https://github.com/FindMalek/Databuddy). Every commit link in this post and the posts it links to points at that fork. Pull request numbers still refer to the upstream repo, which you can no longer open, so the fork commits are the proof.

One limit up front. My clone's history ends on 2026-10-09. Anything that happened upstream after that day is invisible to me, and where it matters I say so.

![Timeline of my Databuddy work from August 20 to October 9, 2026.](/blog/databuddy-what-i-built/timeline.png)

## The timeline

- **Aug 20.** I opened two small PRs the same evening, a funnel cache bug (#636) and a Discord provider (#637). Four commits in 20 minutes, from 18:22 to 18:42.
- **Aug 25.** Both were merged, within about 40 minutes of each other.
- **Aug 27.** I opened the goals dashboard batching PR (#680), after filing issue #679. A fix for two review findings followed 12 minutes later.
- **Sep 27.** #680 was merged, a month later, after a rebase onto a moved `staging`. 594 lines added, 103 removed.
- **Sep 29.** In one evening, between 19:39 and 20:19, I committed four branches: typed alarm triggers (#988), a Jev judge for AI insights (#989), a deterministic seed script (#990) and a destination registry (#991).
- **Oct 5.** A fix for the API exiting at startup when a fingerprint response isn't JSON (#1086).
- **Oct 9.** I merged `staging` into the open branches to keep them alive, and pushed one more small dashboard fix.

By the numbers from `git log`: 21 non-merge commits of mine across all branches, some of them rebased copies of each other. Three squash-merge commits with my name on them in `origin/main` and `origin/staging`.

## What I learned

**The small PRs landed and the big evening didn't.** The two PRs I opened on Aug 20 merged in five days. The one I opened a week later took a month, and it needed a rebase. The four I opened in a single evening on Sep 29 were still open ten days after, as far as my history shows. Review is a queue, and four PRs from the same person is four more things for one maintainer. I'd space them out next time.

**Shared code has edges nobody wrote down.** In #680 it was a filter that only applied to step zero and a step number that wrapped at 255. In #636 it was a cache key written one way and deleted another. Every bug I found was in code that was correct for what it was built for. So I read callers before reusing helpers.

**Fail where the lie happens.** The alarm API said "saved" for alarms that could never fire. The webhook form showed headers the sender dropped. In both cases the fix was to put the check at the moment of saving, not later. See the [alarm triggers](/blog/databuddy-typed-alarm-triggers) post.

**Don't trust discipline, add a test that fails.** The [registry](/blog/databuddy-alarm-destination-registry) is one file. The part that keeps it honest is a test that compares three consumers and fails if they disagree.

**A judge needs calibration before anyone believes it.** The [Jev work](/blog/databuddy-jev-grounding-evals) taught me the most and has the least proof: I have no recorded run. If I did it again I'd start from the four known-bad cases and a labeled set, then build the harness.

**Read the review bot.** On #680 both correctness findings were real, and both were mine.
